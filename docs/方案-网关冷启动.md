# 方案 ・ 网关冷启动（升级 EXE 的唯一合规路径）

> 触发：2026-10-14 升级 EXE 时发现缺口 —— 值守工具只做「重启」（复用旧进程命令行），
> 而规则又禁止「托盘退出后再手工启动」。于是「退出 → 换 EXE → 启动」中间的启动那一步
> 没有合规入口，升级路径是死的。本方案补上 `--start` 冷启动模式。
> 状态：**已执行（2026-10-14；2026-10-19 补充 `--upgrade` 升级重启）**

---

## 一、术语与现状

| 模式 | 前提 | 现在支持吗 |
|---|---|---|
| **重启**（热） | 端口上有正在跑的网关，**复用它的原命令行**再拉起 | ✅ `python tools/restart-gateway.py` |
| **冷启动** | 端口上没有任何网关，需要从零拉起 | ❌ 之前只有 `--check` 与「拒绝」两条路 |

缺口证据（升级流程）：

```
托盘退出（释放 dist\WBRelay.exe 的文件锁）
   → 用新版覆盖 dist\WBRelay.exe
   → 启动   ← 工具拒绝（"只做重启，不做冷启动"），规则又禁止手工启动 ⇒ 死锁
```

## 二、设计

**新增 `--start`（与 `--check` 互斥）**，与重启模式共用同一套值守机制：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | 端口**已有监听** → 拒绝并提示改用普通重启（退出码 2） | 那不是冷启动；两条路径不能混用 |
| 2 | 启动入口**写死两个候选**：`<仓库>\dist\WBRelay.exe`（存在则用）→ 否则 `<仓库>\relay.py`（当前解释器） | 沿用 `validate_start_argv` 白名单；**仍然没有 `--cmd`** |
| 3 | 两个候选都不存在 → 拒绝（退出码 2），提示先打包或用源码方式 | 不猜路径 |
| 4 | 仍走 `validate_start_argv` 二次校验 | 纵深防御：入口不可能带 `--allow-legacy-data` / 归档数据目录 |
| 5 | 仍走「一次性交接文件 + 随机 token + 脱离会话的 worker」 | 会话断了也跑得完；无 token / 重放 / 过期一律拒绝 |
| 6 | worker 侧**再查一次端口**：若已被监听则拒绝启动（退出码 5） | 竞态保护：父进程说没有、worker 起来时已经有了 |
| 7 | 启动后轮询 `/api/state`（默认 60s，`--wait` 可调） | 与重启模式同一就绪判据 |
| 8 | 日志仍落 `%TEMP%\wbrelay-restart-<时间戳>.log` | 与重启模式同一排障入口 |

**不做**：不新增 `--cmd` / `--force` / `--move`；不做通用进程启动器；不写仓库内任何文件；
不碰任何外部进程（R5/R6 不变）。

## 三、`start.bat` 死链修复

`start.bat` 里写的是 `%~dp0WBRelay.exe`（**仓库根目录**），而打包产物一直在 `dist\` —— 根目录那个文件不存在，双击等于死链。

改法：指向 `%~dp0dist\WBRelay.exe`，并在文件缺失时给出明确提示（提示先打包，或改用源码方式 `python relay.py`），不再静默失败。

> 定位：`start.bat` 是**用户手工启动入口**（双击）；`--start` 是**值守进程入口**（脱离会话、
> 带上述全部核验）。两者都能冷启动，升级流程建议用后者。

## 五、与既有红线的关系

| 红线 | 影响 |
|---|---|
| R5（外部进程只显式点击） | 不变 —— 冷启动只拉起本项目网关，不碰任何外部进程 |
| R6（上游只读） | 不变 |
| R7（网关重启走值守进程） | **强化**：冷启动也收进同一个值守进程，手工启动不再是唯一出路 |
| R1（历史/归档数据只读） | 不变 —— 冷启动入口是写死的，且仍过 `validate_start_argv` 的数据目录校验 |

## 七、升级重启 `--upgrade`（2026-10-19 补充）

### 缺口

运行中的 Windows EXE 无法原地覆写，而普通重启会按原命令行再次拉起旧文件
（例如 `dist\WBRelay-1.1.0.exe`）。因此仅靠「冷启动 `--start`」无法完成
「正在运行 → 换新 EXE」的闭环：不先停旧就没有机会替换文件，手工停旧又违反 R7。

### 设计

新增 `python tools/restart-gateway.py --upgrade`：

| # | 规则 |
|---|---|
| 1 | 端口上必须已有本项目网关；先经过与普通重启完全相同的 PID / 可执行路径 / 命令行 / 启动时间 / `/api/state` / 后代归属核验 |
| 2 | 停止旧实例时仍只逐个结束已确认 PID，`taskkill /PID`，不带 `/T` |
| 3 | 启动入口改为写死的 `dist\WBRelay.exe`；不存在时回退 `relay.py` |
| 4 | 保留旧命令行的业务参数（如 `--data-dir`、`--port`）；相对 `--data-dir` 拒绝，避免 cwd 变化改变数据目录 |
| 5 | 仍走一次性交接文件、随机 token、脱离会话 worker、启动后 `/api/state` 轮询 |
| 6 | 仍无 `--cmd` / `--force` / `--move`；`--start` 与 `--upgrade` 互斥 |

### 验收

`tests/test_restart_gateway.py` 新增 G18a–G18f（写死新入口、保留参数、cwd、
源码入口升级、相对数据目录拒绝、参数互斥与旧能力静态审计），
**77 通过 / 0 失败**。真机先用 `--upgrade --check` 确认计划中的启动命令行
为 `dist\WBRelay.exe`，再执行实际升级重启。
