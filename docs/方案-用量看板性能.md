# 方案 ・ 用量看板性能回归修复（1.0.1）

> 状态：已实施（2026-10-14）
> 触发：所有者反馈「用量看板很卡、很慢，筛选的时候最明显」
> 影响版本：1.0.0（回归）；对照版本：10-11 快照版（副本，硬编码汇率）

---

## 一、现象与实测

**为什么「筛选时」最明显**：单次请求耗时 ∝ 命中行数。默认「今日」只有约 1.3 千行，看着正常；
一切到本周 / 本月 / 全部，或按占比最大的供应商（占全部行 93.7%）/ 模型筛选，命中行数仍是
2~3 万量级 —— **筛选几乎不减少开销**。

把两个版本放在**同一份数据、同一个解释器、只读隔离目录**里跑同一段代码（服务端 CPU）：

| 操作 | 10-11 快照版 | 1.0.0 | 差异 |
|---|---|---|---|
| `usage_summary(全部)`（3.4 万行） | 0.18s | 5.80s | 32× |
| `/api/usage?range=all` | 0.22s | 5.68s | 26× |
| `/api/usage?range=all&supplier=<主供应商>` | 0.23s | 5.70s | 25× |
| `/api/usage?range=today` | 0.03s | 0.37s | 12× |

在用实例（冻结 EXE，走真实 socket 与并发）更慢：`range=all` 8.4s；同一请求紧接着复测 17.2s
—— 5 秒定时刷新叠加在途请求，多份聚合被 GIL 串行，互相拖慢。

## 二、根因（一行回归）

`wbrelay/usage.py::_cost_per_request()` 在 1.0.0 把汇率从常量改成**配置项**：

    10-11 快照版：return round(cost_usd * 7.2, 4)
    1.0.0      ：return round(cost_usd * usd_cny_rate(), 4)

而 `usd_cny_rate()` → `load_settings()` → **`copy.deepcopy(settings.json)`**。该函数处在
**逐行的聚合循环**里（`usage_summary()` 的 `for r in filt:`），于是 3.4 万行就深拷贝 3.4 万次配置。

实测归因（同一份数据，只对循环计时）：

| 循环体 | 耗时 | 说明 |
|---|---|---|
| 逐行取汇率（1.0.0） | 3.43s | 占该循环 96% |
| 循环外取一次 | 0.13s | 与 10-11 快照版同量级 |

`_cost_per_request` 的 docstring 早就写着「rate 为本次聚合统一使用的汇率（同上，避免每行重复读配置）」，
但函数签名里没有 `rate` 参数 —— 是**漏做**，不是设计。

**不是瓶颈、本方案不动**的部分：`load_usage_rows()` 的 mtime+size 增量缓存、
`/api/usage` 的三遍 O(N) 扫描、明细排序 —— 实测合计约 0.06s。

## 三、改动

### 3.1 后端：汇率提到循环外（`wbrelay/usage.py`）

- `_cost_per_request(r, profs=None, rate=None)`：新增 `rate` 形参；为 `None` 时才调
  `usd_cny_rate()`（单行调用与既有测试口径不变）
- `usage_summary()`：循环外取一次 `rate = usd_cny_rate()` 并传入每行
- `usage_recent()`：把 `profs` 与 `rate` 提到明细列表生成之外（此前每行各读一次档案与配置）

### 3.2 前端：在途与乱序保护（`dashboard.html`）

- 自动刷新改成「上一轮没回来就不发新的」：`if(!USAGE_INFLIGHT) loadUsage()`
- `loadUsage()` 带请求序号，**只有最新一次的结果允许渲染**：否则旧的自动刷新晚于
  「筛选 / 切范围」的请求返回时，会用未筛选的数据覆盖新结果，并经 `renderRecent()` 的
  `_curUsagePage = rc.page` 把页码改回旧值（数字与表格来回跳）
- 明细翻页走同一条序号线（后发的请求赢）

### 3.3 前端：KPI 成功率口径

`kpi.requests` 本身已含失败行，成功率分母不应再加一次 `errors`。改为
`okPct = (requests - errors) / requests`，与「按模型 / 按供应商」表格里
`requests - errors` 的口径统一。

## 四、不改变的行为

- `usd_cny_rate` 仍是配置项（默认 `7.2`，范围 `0.1`~`100`）：改费率对全部历史记录立即生效
- 历史行仍**不写**汇率 / 成本字段（展示时按当前费率折算）
- KPI / 按模型 / 按供应商 / 明细四个口径仍同源同参数
- `_cost_per_request(r)` 的单行调用行为不变（`rate=None` 时自取当前汇率）
- 核心语义（失败必切换 / 保存即清冷却 / 全败必报错）不在本次改动范围内

## 六、残余风险

- 单次请求仍要扫全量（3.4 万行约 0.06s）。将来若要再降，可考虑按
  「文件 mtime/size + 筛选条件」缓存聚合结果；但那会引入缓存失效面，本轮不做。
- `usage_retention_days` 默认 `0`（永久保留），文件只增不减属策略问题，不在本轮范围。
- 前端的在途 / 乱序保护是**防御性**的：本轮后端修好后单次请求约 0.2s，正常情况下不会
  再堆请求；该保护只是防止数据再次涨大时回到「覆盖新结果」的老问题。
