# 方案 ・ 看板白屏自愈与重启入口修复

> 触发：2026-10-17 出现「前端 EXE 白屏、后端与浏览器访问均正常」的故障；
> 处置时又发现值守工具拒绝重启该实例。本方案同时收口这两件事。
> 状态：**已执行（2026-10-18）**

---

## 一、取证结论（含对上一轮判断的更正）

### 1.1 白屏的直接原因（已确证）

| 证据 | 值 |
|---|---|
| 故障时 WebView2 进程树 | root / gpu / 2×utility / crashpad **共 5 个，唯缺 `--type=renderer`** |
| 宿主窗口 | 存活（`IsWindowVisible=True`、标题正常、窗口几何事件仍在保存） |
| 后端 | `/api/state` 200、`/` 返回完整 140,634 字节看板 |
| 截图 | 窗口框架与标题栏正常，内容区为纯白（白色占比 99%） |

结论：**WebView2 渲染进程消失后，pywebview 没有任何感知与恢复手段**，窗口永久白屏，
只能整进程重启。这是本次要修的缺陷。

### 1.2 对「运行时被覆盖」判断的更正

上一轮曾判断「Windows 半夜自动升级 WebView2 运行时（155.0.4283.45 → .60）覆盖了运行中实例」。
本轮补充取证后**该因果不成立**：

| 反证 | 事实 |
|---|---|
| 版本目录 | `.45` 与 `.60` **并存**，`.45` 的文件未被改动（`EmbeddedBrowserWebView.dll` 仍是 10-08 的时间戳） |
| 崩溃记录 | 旧配置目录 `Local State` 为 `exit_type=Normal`、`system_crash_count=0`；无 WER、无 Crashpad 报告、无 dmp |
| 时间对不上 | 运行时安装于 04:42，而白屏发生在 18:14 之后，中间实例正常使用了十余小时 |

因此：**当前没有足够证据把白屏归因于运行时升级**。真实触发点未知，但「渲染进程会消失、
而 GUI 层无自愈」这一缺陷是确证的，且与触发原因无关 —— 修它就能让同类故障自动恢复。

### 1.3 值守工具拒绝重启的原因（已确证）

```
[退出] 无法确认 PID 84924 是本项目网关：可执行路径既不是 Python 解释器
       也不是 WBRelay.exe：D:\...\dist\WBRelay-1.1.0.exe
```

- 运行中的实例是 `dist\WBRelay-1.1.0.exe`（带版本后缀的副本）
- 工具的白名单常量 `FROZEN_EXE_BASENAME = "wbrelay.exe"` **只认精确文件名**
- 而 `dist\WBRelay.exe` 与它**逐字节一致**（MD5 `cadfa506afd5c70ee78c59ccbbb5ab7f`）
- 自启项 `HKCU\...\Run\WBRelayGateway` 指向带后缀的那个 → 每次开机都复现

后果：R7 规定的唯一合规重启路径对该实例**整条失效**，只能人工托盘退出再手工启动。

## 二、设计

### 2.1 A：值守工具识别仓库内的版本后缀 EXE

只放宽「文件名」这一层，**不放松任何证据链**：

| # | 规则 |
|---|---|
| A1 | 接受 `WBRelay.exe` 或 `WBRelay-<版本>.exe`（版本段必须以数字开头，只含数字/字母/点/连字符） |
| A2 | 仍然必须**位于本仓库目录内**（`REPO_ROOT` 前缀校验不变） |
| A3 | 仍然必须 `/api/state` 协议一致（`suppliers` + `version` + `port` 对得上） |
| A4 | 仍然必须该 PID 正在监听目标端口 |
| A5 | worker 端仍做一次独立身份复核（PID + 可执行路径 + 命令行 + CreationDate） |
| A6 | **冷启动入口保持规范名 `dist\WBRelay.exe` 不变** —— 重启一次即自愈回规范名，自启项随之改写 |
| A7 | 不新增 `--force` / `--cmd`；拒绝理由文案同步更新 |

被拒绝的仍然包括：仓库外的同名文件、`svchost`、仅 basename 雷同的其它进程、`WBRelay-abc.exe`（非数字版本段）。

### 2.2 B：看板渲染进程自愈

新增 `wbrelay/webviewhealth.py`（**纯标准库、只读、不启停任何进程**）：

| 函数 | 作用 | 成本 |
|---|---|---|
| `analyze(procs, own_pid)` | 纯函数：从进程快照算出 WebView2 根 PID 与其子进程数 | 无 |
| `webview_tree(own_pid)` | 用 Toolhelp32 取快照后调 `analyze` | 极低（无子进程） |
| `renderer_pids(host_exe)` | 用 CIM 查 `--type=renderer` 且 `--webview-exe-name` 匹配的进程 | 较高（**只在校验时调用**） |
| `RecoveryPolicy` | 边沿触发：只有「进程树曾经更完整、现在变少」才要求核验 | 无 |

`app.py` 接入一个守护线程（仅在 GUI 模式启动）：

1. 每 10 秒用 Toolhelp32 看一次进程树（空闲时几乎零成本）。
2. 仅当**子进程数从峰值下降**或**根进程消失**时，才用 CIM 做一次权威核验。
3. 确认 renderer 真的没了 → 记日志 → `window.load_url()` 重载看板。
4. 15 秒后复核；仍无 renderer → 记日志 + 回退到系统浏览器打开看板，并停止重试（不刷屏）。
5. 恢复尝试有冷却（30 秒）与次数上限，避免日志/重载风暴。

**不做**：不重启网关进程、不碰外部进程、不写任何文件、不上报任何数据。

## 三、与红线的关系

| 红线 | 影响 |
|---|---|
| R5（外部进程只显式点击） | 不变 —— B 只读进程列表；A 仍只操作已确证的 WBRelay 自身 |
| R6（上游只读） | 不变 |
| R7（网关重启走值守进程） | **强化** —— A 让带版本后缀的在用实例重新纳入值守路径，消除「只能人工重启」的缺口 |
| R1（历史/归档数据只读） | 不变 —— A 的入口白名单与数据目录校验不变 |
| 只读模式零写入 | 不变 —— B 不写盘；新增日志仅走既有 `_log()`（`wb.log` 本就存在） |

## 五、附带修复：桌面快捷方式的黑框（2026-10-18）

用户报告：双击桌面 `WBRelay.lnk` 会出现黑色控制台窗口。

| 取证 | 值 |
|---|---|
| 快捷方式 TargetPath | `python.exe`（系统 Python 的**控制台子系统**解释器） |
| 快捷方式 Arguments | `relay.py`（仓库根目录下的源码入口） |
| PE Subsystem：`python.exe` | **3 = WINDOWS_CUI**（有控制台） |
| PE Subsystem：`dist\WBRelay.exe` | **2 = WINDOWS_GUI**（无控制台，`console=False` 打包） |

改法：把快捷方式指向打包产物（图标、说明、工作目录保持不变；改前留 `.bak` 备份）：

```
TargetPath  : <仓库>\dist\WBRelay.exe
Arguments   : （空）
WorkingDir  : <仓库>
```

副作用（均为预期）：双击后若网关已在运行，会在端口占用检测处**静默退出**（单实例保护，
不弹窗不报错）；同时启动早期会把 `HKCU\...\Run\WBRelayGateway` 重写为当前 EXE，
即自启项自愈为规范名 `dist\WBRelay.exe`。
