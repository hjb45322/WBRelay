# 方案 · 长会话请求体解析与错误语义修复

> 触发：2026-10-19 长会话发送到 `POST /v1/responses` 时收到
> `{"error":{"message":"invalid json","type":"invalid_request_error","code":400}}`。
> 经本地复现，根因不是 Codex 会话历史损坏，而是 WBRelay 把「超过 8 MiB」
> 与「chunked 请求体」都误报成 `invalid json`。
> 状态：代码与运行验证完成；受保护对象基线存在未闭合差异，见第七节。

---

## 一、取证与根因

当前实现位于 `wbrelay/web/server.py`：

1. `MAX_PAYLOAD = 8 * 1024 * 1024`；
2. `_payload()` 只读取单个 `Content-Length`，长度小于等于 0 或超限都返回 `None`；
3. `Transfer-Encoding: chunked` 完全未解析；
4. 所有失败最终统一返回 HTTP 400 `invalid json`。

已观测到的长会话 rollout 大小为 9.15–14.42 MiB，因此典型表现是新会话正常、
长会话或携带父会话上下文的 fork 失败；本地 chunked 请求也能稳定复现同一响应。

这不是会话历史损坏，也不应通过删除会话或无限提高上限来掩盖。

## 二、目标

| # | 目标 | 判定 |
|---|---|---|
| 1 | 14 MiB 左右的长请求可正常进入路由 | 默认上限 32 MiB |
| 2 | `Transfer-Encoding: chunked` 可解析 | 正常 JSON 请求通过 |
| 3 | 错误语义可区分 | 411 / 413 / 400 各有明确消息 |
| 4 | 帧歧义拒绝 | `CL + TE`、重复 `CL`、非法 `TE` 一律 400 |
| 5 | 失败连接不污染下一请求 | 解析失败 `Connection: close`，新连接仍可用 |
| 6 | 排障不泄漏正文/凭据 | 日志只记帧元数据与失败原因 |
| 7 | 既有 API 与核心路由语义不变 | 全量回归通过 |

## 三、协议与实现设计

### 3.1 默认上限与可配置值

- 默认：`32 * 1024 * 1024` 字节（32 MiB）；
- 环境变量：`WBRELAY_MAX_PAYLOAD`，只接受十进制正整数；
- 硬上限：`128 * 1024 * 1024` 字节；
- 非法值回退默认值，超过硬上限按硬上限处理；
- 不允许无限大。

### 3.2 请求帧判定

先检查头，再读取正文：

| 头组合 | 处理 |
|---|---|
| `Content-Length` 恰好一个且为十进制非负整数 | 按声明长度读取 |
| `Transfer-Encoding: chunked` 且无 `Content-Length` | 按 chunk 读取 |
| 两者同时存在 | 400 `invalid request framing` |
| `Content-Length` 重复 / 逗号合并 / 非数字 | 400 `invalid request framing` |
| `Transfer-Encoding` 非单个 `chunked` | 400 `invalid request framing` |
| 两者都缺失 | 411 `length required` |
| `Content-Length` 大于上限 | 413 `payload too large`，不读取正文 |
| chunk 累计大于上限 | 413 `payload too large`，不继续读取 |
| 读取不足声明长度 / chunk 截断 | 400 `incomplete request body` |
| chunk size、CRLF、trailer 格式错误 | 400 `invalid chunked body` |
| 正文不是合法 UTF-8 | 400 `invalid utf-8` |
| UTF-8 合法但 JSON 解析失败 | 400 `invalid json` |

`Content-Length: 0` 与零长度 chunked 正文继续按空对象 `{}` 处理，以保留现有
「可选 JSON 请求体」API 的兼容性。

### 3.3 chunked 约束

- 每个 chunk size 行最大 8192 字节（含 CRLF），支持 `;extension` 但忽略扩展；
- size 只接受十六进制字符；
- 每个 chunk 数据后必须紧跟 CRLF；
- 零 chunk 后读取 trailer，累计最多 8192 字节，直到空行；
- 任何格式错误立即返回 400 并关闭连接。

### 3.4 失败日志

统一记录一行：

```
[WBRelay] payload rejected: content_length=... transfer_encoding=... bytes_read=... limit=... reason=...
```

- 不记录请求正文、prompt、工具输出、Authorization、Bearer token；
- 头值截断显示，避免恶意超长头污染日志；
- 日志仍经过既有 `redact()` 出口。

## 五、测试清单

### 解析器

1. 正常 `Content-Length` JSON；
2. `Content-Length` 恰好等于上限；
3. 上限 + 1 → 413；
4. chunked JSON；
5. chunked 累计超限 → 413；
6. 无长度且非 chunked → 411；
7. `CL + TE` → 400；
8. 重复 `Content-Length` → 400；
9. 截断正文 → 400；
10. chunked 格式错误 → 400；
11. 非法 UTF-8 → 400；
12. 真正 malformed JSON → 400 `invalid json`。

### HTTP 集成

1. > 8 MiB（约 9 MiB）请求不再被判 `invalid json`；
2. chunked 请求进入实际 API 路由；
3. 413 返回 `Connection: close`，随后新连接 `/api/state` 正常；
4. 413 / chunked 超限日志包含帧元数据，不含正文或假凭据；
5. 既有 `tests/test_hardening.py`、`tests/test_http_error_handling.py` 回归；
6. 全仓测试与敏感信息扫描通过。
