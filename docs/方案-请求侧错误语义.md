# 方案 · 请求侧错误语义（413 / 4xx 不得冷却供应商）

> 触发：2026-10-19 20:43–20:47，客户端连续收到
> `503 no usable supplier for model 'deepseek-v4.1-flash' - 供应商都在冷却：WorkBuddy 国内（剩余 31s，最近失败：HTTP 413 HTTP 413）`。
> 状态：代码、隔离测试与真机升级均完成（2026-10-20，见第六、七节）。

---

## 一、取证与根因

### 1.1 现象链

| 时间 | 日志 | 说明 |
|---|---|---|
| 20:43:53 / 20:44:55 / 20:47:41 | `supplier wb-cn failed: HTTP 413 HTTP 413 -> next` | 上游拒收本次请求体 |
| 20:41:59 / 20:52:40 | `supplier wb-cn failed: [WinError 10053] ...` | **同一根因**：上游先拒后关，我们还在写 body |
| 之后 | `503 no usable supplier ... 供应商都在冷却` | 供应商被冷却 60s，后续请求连尝试都没有 |

### 1.2 上游为什么 413

`WorkBuddy 国内` 的 `base_url` 是 `http://127.0.0.1:8788/v1`，背后是另一个本地程序
`wb_proxy.py`（`Server: wb-proxy/1.7.10`）：

- `wb_proxy.py:33`：`MAX_PAYLOAD_BYTES = int(os.environ.get("WB_MAX_PAYLOAD_BYTES", 16*1024*1024))`；
- 超过上限时 `wb_proxy.py:16185` **不读正文、直接 `close_connection = True`**，
  `wb_proxy.py:17191-17196` 回 413。

因此调用方两种表现都存在：**读到 413** 或 **写 body 时连接被掐断（10053/10054）**。

本地实测 8788 阈值（假模型名，仅探边界）：

| 请求体 | 上游响应 |
|---|---|
| 1 MiB / 4 MiB | 200 |
| 8 / 12 / 13 / 14 / 15 MiB | 400 `prompt is too long: 1176612…2094116 tokens > 1048576 maximum` |
| 16 MiB 及以上 | 连接重置（即 413 早退路径） |

> 结论：真正的墙是 **1.048576M token**；16 MiB 只是字节墙。**调高 `WB_MAX_PAYLOAD_BYTES` 不能解决 token 超限**，
> 所以本方案不改上游（R5：不动外部进程），只修 WBRelay 的错误语义。

### 1.3 WBRelay 的问题

`wbrelay/web/api_v1.py` 旧实现：

1. `_supplier_dispatch` 里**任何** `HTTPError` 都 `supplier_mark_cool(...)`（默认 60s），
   413 这种「请求体太大」也被当成供应商故障；
2. 上游早退时读不到错误正文，`last_error` 回落到 `"HTTP %d"`，再被 `reason="HTTP %d %s"`
   拼一次 → 文案变成 `HTTP 413 HTTP 413`；
3. 冷却窗口内的请求走不到路由，只能返回 503，把「这次请求太大」伪装成「供应商全挂」。

一次超限请求 = 该供应商 60 秒内**所有模型**不可用。这是本轮要修的核心。

## 二、目标

| # | 目标 | 判定 |
|---|---|---|
| 1 | 请求侧拒绝不再冷却供应商 | 413 / 400 / 404 / 422 之后 `/api/state` 的 `cooling` 仍为 false |
| 2 | 413 把真实原因交给客户端 | 客户端拿到 HTTP 413 + 「请求体约 X MiB，请精简/新建会话」，不是 503 |
| 3 | 上游「先拒后关」按请求侧处理 | 已推送 ≥ 8 MiB 请求体时连接被断开 → 不冷却，返回 413 |
| 4 | 冷却原因文案不再重复状态码 | `HTTP 413`，而不是 `HTTP 413 HTTP 413` |
| 5 | 供应商侧失败仍按原语义冷却 | 5xx / 429 / 401 / 403 / 网络异常（小 body）行为不变 |
| 6 | 核心语义不被改写 | 「失败必切换」「保存即清冷却」「全败必报错」回归全绿 |

## 三、设计

### 3.1 失败分类

| 上游状态 | 判定 | 冷却 | 是否继续切换 |
|---|---|---|---|
| `413` | 请求侧（体过大） | 否 | **否**，立即把原因交给客户端 |
| `400` / `404` / `422` | 请求侧（参数/路径/语义不合规） | 否 | 是（保持「失败必切换」） |
| `429` | 供应商侧（限流） | 是（`cooldown_429_sec`） | 是 |
| `401` / `403` | 供应商侧（凭据/权限） | 是 | 是 |
| `5xx` | 供应商侧 | 是 | 是 |
| 发送阶段连接被重置且**已推送 ≥ 8 MiB** | 请求侧（上游按上限先拒后关） | 否 | 否，返回 413 |
| 其它网络异常 | 供应商侧 | 是 | 是 |

`413` 不再切换的理由：这是对**这一份请求体**的判决，换一家一般也是同样的判决；
继续切换只会再推一遍 16 MiB，把客户端等待时间拉长，并且掩盖真实原因。

### 3.2 8 MiB 阈值的依据

上游在 body 超限时**先拒后关**，客户端拿到的只是 `WinError 10053/10054`，无法从异常类型区分
「上游拒收」与「网络抖动」。因此用「已经推了多少字节」做判据：

- 观察到 8 MiB 时上游已经在 token 层面顶到 1.048M 上限，16 MiB 触发字节墙；
- 因此 `LARGE_REQUEST_BODY = 8 MiB` 是**保守下限**：只有体量已经到这个量级的连接中断才归为请求侧；
- 小请求的网络异常仍按供应商故障冷却（第 5 条不变）。

### 3.3 错误正文

413 返回给客户端的内容（`type=invalid_request_error`，`code=413`）：

```
上游（<供应商名>）拒绝了本次请求：请求体约 17.4 MiB，HTTP 413：payload too large (...)。
请精简会话历史或新建会话后重试；该供应商未被标记为故障。
```

不带正文、不带凭据；日志只记体量与状态码。

### 3.4 用量口径

413 记一条 `status=413 / error=true / realm="none"` —— 它既不是某家供应商的健康度，
也不属于「全败」（`supplier:all_failed`），与既有「未路由成功」口径保持一致。
